# 📚 概念学习・Pi Agent 架构全景

> 基于一位博主分享的 Pi Agent 架构解读做的串讲。Pi Agent 是一个比较好的开源项目，讲述者按它的全景导图逐层讲解。

## 是什么（What）

- **一句话定义**：Pi Agent 是一个用非常少的代码搭出来的开源 Agent 框架（Agent Harness），给大模型装上 "外置骨骼机甲"。
- **生态位**：和 Claude Code、OpenCode 属于同一生态位，但对应场景不同；OpenCode 内部其实也是基于 Pydantic 做的。
- **核心三件套**：
    1. **Agent Loop**（内核 / 循环）
    2. **工具系统**（手脚）
    3. **简洁的 UI**（外部显示终端）
- **比喻**：大模型是大脑，Harness 是包裹在大脑外面的整套 "驾驭工程"—— 手脚工具、显示终端、记忆机制、上下文工程、Skill、检查机制、安全护栏。

## 为什么（Why）

- 现在大模型本身能力已经很强，**发挥能力之余，安全越来越重要**。
- 在金融、信贷这类高合规场景，"合规、符合监管、安全可控" 比单纯的能力更重要。
- 厂商（Provider）碎片化严重：要对接多个模型供应商，认证、负载、降级、生产维稳都是麻烦事，需要统一抽象层。
- 旧的事件机制（生产者驱动）会阻塞、堆内存，不适合大模型流式输出，所以要换成消费者驱动的事件流。

## 怎么用（How）—— 整体架构

### 三层架构

- **产品层（终端 UI）**：人和 Agent 交互的入口，配置额外能力，外层 UI 即可。
- **运行时（Runtime）**：真正跑起来的 Agent Loop—— 自己决定用哪些工具、状态管理、事件暴露、执行调度。
- **核心（大模型调用）**：用抽象层对接所有供应商；用一个统一的 `Model` 对象描述接口，`Stream` 做统一流式输入入口。Provider 碎片化问题被这层抹平，业务只关心怎么写，具体对接由框架完成（也可以直接用 LiteLLM 这类成熟方案替代）。

### Agent Loop：外循环 + 内循环

- **外循环**：负责和人通信，是一个消息队列循环；接收外部新输入。
- **内循环**：大模型和 Harness 的真正交互，处理某一条消息 —— 判断是停止、报错，还是要调工具。要调工具就一直循环，调完回来；发现队列里还有消息就继续；回到外循环再看外部有没有新消息。
- **生命周期钩子**：`agent start/end`、`message`、是否停止 / 报错 / 调工具等节点全部暴露。可以做全链路插桩监控、安全校验、结束动作、自定义上下文管理 —— 这是 "安全可控地插入" 的关键位置。

### 工具系统

- 用统一的 `AgentError` 封装。
- 自定义字段先定义好注册进状态，每次自动带上。
- **`before-tool-call` 前置拦截 hook**：调工具之前先拦一道，防止 Prompt Injection 等危险；执行完在后处理里回收。

### 消息系统：两套消息模型

- **AgentMessage（内部态）**：KV 结构化，语义清晰 —— 区分用户消息、AI 消息、工具结果、状态消息，以及哪块是压缩摘要、哪块是原始消息。信息全，但有冗余，**不适合直接喂给大模型**。
- **Message（给模型的标准格式）**：内部消息清洗、取舍后转成标准格式，大模型能更清晰地理解整个过程。
- **关键设计 —— 最晚转换**：
    - 如果立刻把内部消息转成标准 Message，再拿去做存储和前端渲染，**信息会丢失**（UI 渲染不出更丰富的内容）。
    - 所以是**先存、先渲染、先 fork 分支，最后一刻才转成模型格式**，信息最全面。
    - 压缩摘要（compaction/summary）和近期真实结果在内部是**分字段**存的；到给模型时才合成一个字段。

### 事件流 EventStream（自研 evstream）

- 自带 "结果" 概念，传输过程中就能解析、最后统一输出。
- **背压（Backpressure），以消费者为主**：
    - 老做法是生产者为主 —— 触发事件就同步调所有监听器，会阻塞、堆内存，不适合流式输出。
    - 新做法是消费者为主：消息堆积多了，消费者可以主动告诉生产者 "先别生产了 / 等一等"，不让消息一直堆在内存里。
- 两种消费方式：
    - **`for await`**：消费者视角，来一块处理一块（适合流式）。
    - **回调**：同步触发所有监听器，会阻塞、堵内存，不适合流式和异步场景。

### 上下文工程（最核心）

- **本质问题是信息密度**：在有限上下文窗口里，把无限对话的信息密度做到最好。讲述者反复强调 ——**Agent 整体就是在上下文工程上做文章**。
- **压缩（Compact）**：
    - 一般设阈值（比如 60%–70%），超过就触发压缩。
    - 策略：**近期消息保留，早期压成结构化摘要**（用大模型筛选）；Pydantic 内部设计了好几个字段做结构化摘要压缩，最后 = 摘要 + 近期消息替换整个上下文。
    - **摘要是结构化的任务摘要**：目标、要求、已完成什么、没完成什么 —— 对长任务尤其关键。
- **`transformContext` 钩子**：每次调用前对上下文做最后处理（也是生命周期钩子，可异步）—— 可以删掉旧消息、注入 RAG 结果、压缩中间工具结果。Claude Code 的常见实践是把相同 / 相近工具结果合并清理、压缩，只给模型看摘要。
- **流派对比**：
    - Pydantic：结构化压缩。
    - Claude Code / OpenCode 可能有更多样的上下文操作。
    - OpenAI 最近倾向**不压缩**，直接用检索算法把上下文置换为更合适的内容 —— 因为压缩总会有损。

### 会话管理

- 会话保存成**一棵树（工作树）**，支持跨会话、fork、走不同分支。
- 进入新分支时，对前面做一次全量摘要压缩，把摘要作为新分支的起点。

### 扩展系统

- 把 **Skills、实例化（Instantiate）、提示模板**这三类提升为**一等公民（first-class citizen）**，按一等公民来设计，存在不同地方。
- 注入方式：在生命周期里注入 —— 启动时扫描扩展、加载模块。
- **插件机制差异**：
    - Pi Agent 用 TypeScript 插件系统，新插件启用通常需要**重启**才能加载。
    - 较新的 harness 采用某种 "create" 编程范式，支持**动态热加载、热插拔**—— 不停机就能给自己加插件，更突出 "自定义 Agent 的自成长"。
    - 讲述者补充：自己用 OpenCode 前些阵子还需要重启网关，推测 Pi Agent 大概率也要冷启动，但最新版本可能已支持动态加载。

### Provider 与认证

- 比较简单：可以直接用开源的 **LiteLLM** 统一对接多个模型供应商，认证、负载均衡、降级、生产维稳都交给它。
- Pydantic 自己也写了一套跨 API 兼容、模型注册的抽象层，可直接用。

## 对比（Diff）

- **与 Claude Code / OpenCode 同生态位、不同场景**：三者都是 Agent Harness；Claude Code 用 hook 做扩展，Pi Agent 用插件 —— 只要生命周期暴露得好、事件 hook 做得细，插件也能做到很细腻的定制。
- **插件热加载 vs 冷启动**：Pydantic（TS 插件，需重启）→ 新范式（create，支持热插拔，不停机成长）。
- **事件流：生产者驱动 vs 消费者驱动**：后者带背压，适合大模型流式输出。
- **上下文策略：压缩 vs 置换**：Pydantic 走结构化压缩；OpenAI 倾向检索式置换，认为压缩有损。
- **任务清单（Claude Code 对比）**：有两套 ——Todo List（内存级任务清单）和持久化任务列表（可跨会话）。
