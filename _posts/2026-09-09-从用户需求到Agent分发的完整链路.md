## 1. 链路总览

```
┌─────────────────────────────────────────────────────────────────────┐
│                    资产入库与预处理阶段                               │
│              （静态质量准入 + 能力图谱构建）                           │
└─────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────┐
│                    用户意图理解阶段                                   │
│         （意图解析 → 置信度判断 → 澄清/直接推荐）                      │
└─────────────────────────────────────────────────────────────────────┘
                                    ↓
┌─────────────────────────────────────────────────────────────────────┐
│                    候选召回阶段                                       │
│      （多路召回 → 硬约束过滤 → 质量门槛过滤 → 候选池）                 │

                                    ↓
┌─────────────────────────────────────────────────────────────────────┐
│                    排序与个性化阶段                                   │

                                    ↓

│                    推荐生成与交互阶段                                 │

                                    ↑                                                  │
└───────────────────────────────────┴──────────────────────────────────┘
```

## 2. 各阶段详解：谁来判断，为什么？

---

### 阶段一：资产入库与预处理

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 静态质量检查（字段完整度、格式规范、版本号合规） | **规则** | 字段是否齐全、描述是否达到最小长度、版本号是否符合语义化规范 | 判断标准明确、无歧义、可穷举。规则执行成本极低、速度快、无主观偏差。人工审核在这里是浪费。 |
| 安全合规扫描（漏洞、权限、隐私） | **规则 + 模型** | 规则执行硬性安全项（如“不得请求 root 权限”），模型进行代码安全扫描和敏感数据流分析 | 安全项大多可明确定义为布尔判断，规则足够。代码级漏洞则需要模型辅助（如 LLM 分析或静态分析工具），但最终结论仍以规则化为“通过/不通过”输出，减少灰色地带。 |
| 内容合规审核（描述是否违规、是否涉及禁止领域） | **模型 + 人工** | 模型做初筛，标记疑似违规内容；人工对边界案例做终审 | 合规判断涉及价值观、语境和文化敏感性，纯模型可能误判（尤其灰色地带）。模型做初筛降低人工量，人工只在模型不确定或创作者申诉时介入。 |
| 能力标签抽取（该资产能做什么、输入输出、依赖） | **模型 + 创作者人工确认** | LLM 从描述、README、代码中自动抽取能力标签；创作者在发布时确认或修正 | 自动抽取可规模化，但能力标签直接影响后续匹配质量，必须由最了解资产的创作者确认。人工确认是低成本、高收益的校验环节。 |
| 图谱节点创建与关系建立 | **规则 + 模型** | 规则定义图谱 schema 和关系类型；模型自动发现资产间的相似、替代、组合关系 | 图谱构建是结构化的确定性操作，规则保证一致性。关系发现是语义判断，需要模型。但关系是否正确由后续用户行为数据持续验证和纠偏。 |

**本阶段的核心原则**：能用规则绝不浪费模型和人力；模型负责规模化初筛；人工只出现在“边界不确定”和“高价值决策点”。

### 阶段二：用户意图理解

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 自然语言解析（用户输入 → 意图槽位） | **模型** | 将用户文本解析为任务类型、对象、约束、偏好等结构化槽位 | 自然语言理解是典型的非结构化→结构化映射问题，规则无法覆盖开放域表达的无限变体。这是 LLM 的核心能力所在。 |
| 意图置信度计算 | **模型 + 规则** | 模型输出槽位填充的置信度；规则根据置信度和槽位完整度决定是否触发澄清 | 置信度计算需要模型给出不确定性估计。但“何时澄清”是产品策略决策，应通过规则明确阈值（如置信度 < 0.7 触发），保证行为可预期、可调优。 |
| 澄清问题生成（问什么、怎么问） | **模型** | 基于当前已知信息，生成信息增益最高的 1-2 个澄清问题 | 问题生成是动态的自然语言生成任务，必须由模型完成。但“问不问”“问几个”由规则控制，防止模型过度追问。 |
| 澄清必要性判断（跳过多轮直接推荐 vs 继续澄清） | **规则** | 判断条件：置信度是否达标、已澄清轮数是否超过上限、用户是否选择跳过 | 这是产品体验策略，需要在“匹配精度”和“用户耐心”之间做确定性权衡。规则保证行为一致、可监控、可 A/B 测试。 |
| 用户画像加载与应用（新手/专家、偏好、约束） | **规则 + 模型** | 规则决定加载哪些画像维度；模型将画像特征与当前意图融合 | 画像的存储和调用是工程确定性操作。画像如何影响意图理解是模型的特征融合问题。 |
| 历史对话摘要调用 | **模型** | 从跨会话记忆中检索与当前任务相关的历史摘要 | 相关性判断是语义任务，需要模型检索。但“是否启用历史记忆”由规则控制（如用户关闭个性化时不调用）。 |

**本阶段的核心原则**：模型负责“理解”，规则负责“决策”。理解是语义问题，决策是策略问题。模型输出的不确定性由规则来兜底，保证系统行为可预期。

### 阶段三：候选召回

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 关键词召回（BM25） | **规则** | 精确词汇匹配，基于倒排索引的确定性检索 | 纯规则计算，无需判断“语义相似”，只做字面匹配。速度快、结果可复现。 |
| 语义向量召回（Embedding） | **模型** | 将用户意图和资产描述映射到向量空间，计算语义相似度 | 语义相似性判断是模型的核心价值。但模型只负责“打分”，不做最终是否入选的决策。 |
| 图谱召回（能力匹配 + 关系遍历） | **规则 + 模型** | 规则执行图谱查询（如“找到具有[数据清洗+Excel]能力的节点”）；模型判断节点间的关系强度 | 图谱查询是确定性操作。关系强度（如“资产A是否可替代资产B”）是语义判断，需要模型辅助，但由用户行为数据持续校准。 |
| 硬约束过滤（依赖不满足、权限冲突、用户明确排除项） | **规则** | 用户无 API Key → 过滤需要 API 的资产；用户设置了“仅本地执行” → 过滤云端资产 | 硬约束是可枚举的布尔条件，规则执行保证零容错。模型在这里反而可能出错。 |
| 质量门槛过滤（一票否决、最低 QS、完成率下限、投诉率上限） | **规则** | 过滤不符合推荐准入条件的资产 | 质量门槛是预设的产品决策，必须确定性执行。任何“灵活性”都会导致劣质资产绕过门槛，损害用户信任。 |
| 候选池大小判断（是否触发降级放宽） | **规则** | 候选数 < N → 按预设降级序列逐步放宽非硬性门槛 | 降级策略是产品预先定义好的策略链，规则执行保证一致性。人工不应实时介入（延迟太高），模型不应自行决定放宽（不可控）。 |

**本阶段的核心原则**：召回用模型做“软判断”（相似度），过滤用规则做“硬判断”（是/否）。模型的输出是分数，规则的输出是布尔值。所有“能不能进候选池”的决策必须是规则，保证任何资产被过滤掉都有明确的、可追溯的原因。

### 阶段四：排序与个性化

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 粗排（从数百候选到 Top 50-100） | **模型（轻量）** | 用轻量模型（如双塔、XGBoost）对候选做初步相关性打分 | 粗排需要处理大量候选，LLM 逐一打分成本过高。轻量模型在速度和效果之间取平衡点。 |
| 精排（从 Top 50-100 到 Top 10-20） | **模型（深度/LLM）** | 综合质量分、匹配度、用户画像、场景信号做细粒度打分 | 精排是决定用户体验的关键环节，需要最丰富的特征和最精细的判断。模型承担复杂非线性判断是合适的。 |
| 质量调节因子应用 | **规则** | 将质量评估框架输出的 QS、完成率、投诉率、置信度按预设公式折算为排序乘数 | 质量因子如何影响排序是产品策略（如“完成率低于 60% 乘 0.3”），必须规则化，保证可解释、可调优。模型不应自行决定质量的权重。 |
| 多样性约束（同创作者上限、同类型上限） | **规则** | 对推荐列表施加硬性多样性约束 | 多样性是确定的约束条件，规则执行即可。 |
| 探索/利用调节 | **规则 + 模型** | 规则根据置信度决定探索概率和探索位次上限；模型在探索池内做排序 | 探索策略（何时探索、探索多少）是产品决策，规则控制。探索池内的排序仍需模型的匹配能力。 |
| 反马太调节（曝光衰减、潜力加成、长尾保底） | **规则** | 基于曝光量、曝光-质量偏差等预设阈值，施加加权或衰减系数 | 反马太机制是产品生态策略，必须以规则形式明确执行。如果让模型自行决定“是否扶持长尾”，行为不可控且无法向创作者解释。 |
| 最终排序输出 | **规则** | 将各调节因子合并为最终公式，计算最终排序 | 最终排序公式是产品策略的确定性表达。规则保证每次决策可复现、可审计、可申诉。 |

**本阶段的核心原则**：模型负责“打分”，规则负责“排序”。模型的输出是一个个独立的分数，规则的输出是最终的排序决策。这样设计的原因是：排序决策直接影响生态公平和创作者利益，必须可解释、可审计、可申诉。模型的黑盒打分可以作为输入特征，但不能作为最终决策的直接依据。

### 阶段五：推荐生成与交互

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 推荐理由生成 | **模型** | 基于排序依据，生成面向用户的自然语言解释 | 推荐理由是自然语言生成任务，模型是唯一合理的承担者。但生成的模板和核心要素由规则约束（如必须包含“完成率”和“场景匹配度”两个维度）。 |
| 风险提示（质量不完美时） | **规则** | 当资产完成率低于阈值或投诉率偏高时，自动附带风险提示文案 | 风险提示的触发条件是预设阈值，规则执行。文案可以是模板化的，不需要模型生成。 |
| 主动推荐触发 | **规则 + 模型** | 规则控制触发时机（如时间驱动、任务失败驱动）和频次上限；模型判断当前用户与候选资产的匹配度 | “什么时候推”是产品节奏策略，规则控制。“推什么”是匹配问题，模型判断。 |
| 用户反馈入口 | **规则** | 提供“有用/无用”“不感兴趣”“不再推荐此类”等固定反馈选项 | 反馈收集是交互设计，规则定义。 |
| 多轮对话管理 | **规则 + 模型** | 规则管理对话状态机（澄清中/推荐中/反馈中）；模型生成每轮的具体内容 | 对话流程是确定性状态机，规则管理。每轮回复内容需要自然语言生成，模型完成。 |

**本阶段的核心原则**：模型负责“说话”，规则负责“何时说话、说什么类型的话”。所有面向用户的交互节奏和触发条件都是产品策略，规则化保证一致性和可控性。

### 阶段六：反馈闭环与动态更新

| 子环节 | 判断主体 | 具体判断内容 | 为什么由它承担 |
|---|---|---|---|
| 行为数据回收（曝光→点击→使用→成功/失败→评分） | **规则** | 统一埋点、统一口径、事件管道 | 数据采集是工程确定性操作，规则定义。 |
| 质量分子分更新 | **规则** | 按预设公式（如威尔逊下界、贝叶斯平均）更新各维度子分 | 分数更新公式是产品预设的统计方法，规则执行，保证所有资产在相同逻辑下被评估。 |
| 综合质量分重算 | **规则** | 按预设权重和公式重算 QS | 同上。 |
| 异常检测（投诉激增、成功率骤降） | **模型 + 规则** | 模型检测统计异常（如时间序列异常检测）；规则根据异常幅度触发不同级别的响应 | 异常检测需要模型识别复杂模式。但“触发什么响应”（如降权、下架、通知创作者）是产品策略，规则执行。 |
| 降权/下架决策 | **规则 + 人工** | 规则执行自动降权和下架的预设条件；人工对下架决策进行复审（或在创作者申诉时介入） | 自动降权可以由规则执行（影响可逆）。下架是影响创作者权益的重大决策，规则触发后需人工复审，防止误伤。 |
| 创作者申诉处理 | **人工 + 模型** | 创作者提交申诉；模型辅助整理证据（如质量报告、行为数据摘要）；人工做出最终裁定 | 申诉处理涉及公平性和信任感，最终决策权必须由人掌握。模型可辅助证据整理，但不能替代人的判断。 |
| 评估框架自身校准（阈值调整、权重调整） | **人工 + 模型** | 模型分析各阈值和权重对业务指标的影响；人工决定是否调整及如何调整 | 框架参数变更影响全平台生态，属于重大产品决策。数据分析可由模型辅助，决策权在人。 |
| 推荐效果 A/B 实验 | **规则 + 人工** | 规则执行实验分流和数据收集；人工设计实验方案、解读结果、决定是否全量 | 实验设计需要业务理解和创造性判断，人工主导。实验执行是工程确定性操作，规则管理。 |

**本阶段的核心原则**：数据更新用规则，异常识别用模型，重大决策用人工。规则保证日常运转的效率和一致性；模型在复杂模式识别上补充规则的不足；人工只在“影响大且难以自动判断”的节点上介入。

## 3. 判断主体分工总览

| 判断主体 | 承担的判断类型 | 核心逻辑 |
|---|---|---|
| **规则** | 硬约束过滤、阈值判断、策略执行、公式计算、状态机管理、触发性动作 | 可枚举、可穷举、需要确定性、需要零容忍、需要可解释可审计的判断。规则是最可靠、最可控、成本最低的判断主体。 |
| **模型** | 语义理解、相似度计算、特征融合、异常检测、自然语言生成、知识抽取 | 非结构化→结构化的映射、高维特征的非线性组合、模糊语义判断。模型是唯一能规模化处理开放域语义问题的主体。 |
| **人工** | 合规终审、下架复审、申诉裁定、框架参数调整、实验设计决策 | 涉及价值观判断、公平性权衡、创作者权益、平台生态战略的高影响决策。人是最终信任锚点，但在自动化成熟时不参与日常流转。 |

## 4. 为什么这样分配？——设计逻辑

### 4.1 规则优先原则

**凡是能用规则的地方，绝不用模型或人工。**

- 规则是确定性的，行为可预期，结果可复现。
- 规则的成本极低，一条规则可以服务全平台所有资产和用户。
- 规则天然可解释：任何被过滤、降权、加权的资产，都能追溯到具体是哪条规则、哪个阈值触发的。
- 规则可 A/B 测试，可版本化管理，可灰度发布。

### 4.2 模型补充原则

**凡是涉及语义、模糊性、非结构化输入的地方，必须用模型。**

- 自然语言理解、语义相似度、异常模式识别是规则无法覆盖的。
- 模型承担的是“打分”和“理解”的角色，而非“决策”的角色。
- 模型的输出始终被规则包裹在明确的边界之内。

### 4.3 人工兜底原则

**凡是影响大、不可逆、涉及信任和公平的地方，人工必须介入。**

- 下架资产、拒绝申诉、调整全局阈值，这些都是影响创作者生计和平台生态的决策。
- 自动化可以提出建议，但最终决策权由人掌握。
- 人工介入的比例应随系统成熟度逐步降低，但不归零。

### 4.4 成本效能逻辑

| 判断主体 | 单次成本 | 延迟 | 可扩展性 | 适用频率 |
|---|---|---|---|---|
| 规则 | 极低（几乎为0） | 毫秒级 | 无限 | 全量实时 |
| 模型 | 中等（LLM 调用费用） | 百毫秒–秒级 | 高（但有并发限制） | 高频但非全量 |
| 人工 | 高（人力成本+时间） | 小时–天级 | 低（受人力限制） | 低频高价值节点 |

这条链路的设计将**成本最低的规则**作为默认判断主体，**中等成本的模型**用于规则无法覆盖的语义判断，**高成本的人工**仅在不可替代的关键节点介入。这种梯度保证了整个系统在规模化运转的同时，控制成本在可持续范围内。

## 5. 链路中的关键决策点清单

以下列出全链路中所有“是否值得继续分发”相关的判断点，及各自的判断主体：

| # | 决策点 | 判断主体 | 触发时机 | 可申诉性 |
|---|---|---|---|---|
| 1 | 资产是否通过入库安全合规检查 | 规则+模型+人工（边界） | 首次发布、版本更新 | 是 |
| 2 | 资产是否进入推荐候选池 | 规则 | 每次推荐请求 | 是 |
| 3 | 资产在推荐列表中的位置 | 规则（排序公式） | 每次推荐请求 | 否（但可查证据） |
| 4 | 资产是否获得探索曝光 | 规则（置信度阈值） | 每次推荐请求 | 否（策略性） |

## 6. 总结

这条链路的本质是将“判断力”分层：

- **规则层**承担所有确定性的、策略性的、需要零容忍的判断，构成系统的骨架；
- **模型层**承担所有语义性的、模糊性的、非结构化的理解与打分，构成系统的血肉；
- **人工层**承担所有高影响的、涉及信任与公平的终审决策，构成系统的信任锚点。

三者的协作保证了系统在**规模化、可控性、可解释性、成本效能**之间的平衡。任何一个判断主体被过度依赖，都会导致系统失衡：过度依赖规则会僵化，过度依赖模型会失控，过度依赖人工会崩溃。
