      • 核心问题：如何提高利用率
    • 碎片化与空闲

      • GPU 利用率不拉满、存在空闲阶段

  • 通用底盘：prefill + decode 与 KV Cache
    • 推理两阶段
      • prefill：处理所有输入 token
      • decode：自回归逐个生成新 token
    • KV Cache：缓存历史的 K/V
      • 本质：每个 token 与前面所有 token 做 QKV 交互
      • 前缀（如 system prompt）每次都一样 → 重复计算浪费
      • 解法：把算过的 K/V 存起来，命中直接取用
      • 未命中的 K/V 仍需重新计算
    • 固定长度缓存的老问题
      • 预设过短 → 缓存不够用、命中率低、频繁交换
      • 预设过长 → 内部碎片；与 batch 不成比例 → 外部碎片
      • 本质：物理地址过于连续（数组 → 链表类比）
    • 碎片规律
      • 高并发 + 短序列 → 内部碎片多
      • 低并发 + 长序列 → 内部碎片低
  • vLLM：生态最广的先行者
    • 核心技术一：PagedAttention
      • 仿操作系统虚拟页管理（虚拟内存机制）
      • 逻辑页 → 动态物理地址，无需预分配连续地址
      • 效果：消除显存碎片、提高显存利用率、吞吐上升
    • 核心技术二：Continuous Batching
      • 动态批处理，token 逐个流出（流式）
      • 不用等整个 batch 结束，GPU 不空等
      • 提高并发，实现请求的连续调度
    • 实现细节
      • KV cache 切分成固定 block，存于不同页
      • memory management：请求真正生成 token 时才分配新 block
      • 调度器：每个迭代重新评估哪些请求进入 batch
      • 贪心策略保证已生成 token 立即入队
      • 完成即移除、新请求下一迭代补位，GPU 持续高负载
    • 三大指标
      • 吞吐量：每秒输出 token 数
      • TTFT：首 token 延迟
      • TPOT：每 token 延迟
    • 特点
      • 出现早、社区生态好
      • 兼容 OpenAI API，迁移可复用原有流程
  • SGLang：前缀复用的极致派
    • 核心一：RadixAttention
      • 名字像 radix tree（前缀树），用树结构存前缀缓存
      • 实现前缀 KV cache 的高效复用
    • 核心二：DSL
      • 以代码形式描述生成流程
    • 擅长场景
      • 多轮对话（system prompt 相同）
      • 编码（文件前缀相似）
      • Agent 工具调用（原生支持结构化输出）
      • 复杂程序调度
    • 与 vLLM 的分水岭
      • 前缀重复度越高，优势越大
      • 前缀重叠低时，两者吞吐相当
  • TensorRT-LLM：英伟达上的榨干派
    • 编译期优化
      • AOT：编译时优化
      • 深度绑定英伟达 GPU
    • 算子级融合
      • 卷积 / attention / transformer 算子合并加速
      • 榨干 GPU 性能
    • 适用
      • 英伟达卡 + 追求极致性能
  • ONNX Runtime：通用派
    • 跨平台：CPU / GPU / NPU
    • 跨模型：非大模型场景也覆盖
    • 运行时图优化
    • 适用：边缘设备、多模型混合部署
  • 选型决策
    • 四维判断
      • 场景 × 硬件 × 生态 × 团队能力
    • 结论
      • 通用高吞吐、上手快、要生态 → vLLM
      • 复杂程序 / Agent / 高前缀复用 → SGLang
      • 极致性能 + 英伟达硬件 → TensorRT-LLM
      • 通用多模型 / CPU / 边缘 → ONNX Runtime
